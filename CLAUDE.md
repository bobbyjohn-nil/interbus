# CLAUDE.md

Working rules for Claude sessions on interbus, a calm bus-company game on real Boston: flat 2D that tilts into 3D, in light and dark; a GitHub Pages preview now, a free Steam demo for macOS and Windows at Next Fest in June 2027, then Steam as the only release. Read [docs/STATUS.md](docs/STATUS.md) first (what is live, in progress, waiting on the owner and next), then [PLAN.md](PLAN.md) §0 and [docs/specs/current.md](docs/specs/current.md), the current milestone's spec; search [docs/DECISIONS.md](docs/DECISIONS.md) (over 300 KB) for the decisions a task touches rather than reading it whole (D27). If they disagree, `docs/DECISIONS.md` and `docs/SCOPE.md` win over the plan.

## Writing in this repo (it is public)

- Never write the owner's or the co-developer's real names. Write "the owner" (or "you" when addressing the owner) and "the artist" or "the co-developer". No gendered pronouns for either.
- Nothing about age, school, family, other personal projects, or private spreadsheets and documents.
- No machine-local paths (temp folders, home directories, scratchpads). Cite prior work as `Intralines@7af45b1:path` (V1), `Intralines_City_dep@archive/intralines-city-v1:path` (V2) or `Intralines_City@dc63602:path` (V3), or by lesson and bug ID from `docs/history/`.
- Every web fact carries its URL and the date checked. Fees, limits and policies say "check before relying on it".
- `docs/history/` is a frozen record. Never edit it.

## How sessions work

- **One session owns `main`.** It pushes its branch often and merges small PRs on green CI, with merge commits only (squash and rebase merges are off). Other sessions stay read-only or on their own branch ([PR-07](docs/history/lessons-ledger.md), [PR-08](docs/history/lessons-ledger.md)).
- **The status file.** [docs/STATUS.md](docs/STATUS.md) is the handoff between sessions and context windows: every PR that merges updates it, so nothing lives only in a conversation. It holds only what is live, waiting, in progress and next; finished work lives in git, `CHANGELOG.md` and `docs/DECISIONS.md` (D27). It also holds the owner's autonomy protocol: a check-in Routine every two hours that carries work on through usage-limit pauses without the owner, and how a new session takes it over.
- **No agent crew.** One session does the work ([PR-04](docs/history/lessons-ledger.md)). Subagents and workflows run only where they save more than they cost: an audit's finders, and a fix batch's fixer with one reviewer. The fixer's failing-first test is a finding's reproduction, so there is no separate verifier, and CI is waited on through the PR's events, never by polling (D27).
- **Short specs.** One spec per milestone in `docs/specs/current.md`, ≤150 lines, with magnitudes and a cut line ([SC-06](docs/history/lessons-ledger.md), [SC-07](docs/history/lessons-ledger.md)).
- **Restate feedback first.** Restate the owner's feedback in one sentence before building on it. If measurement suggests a better route, say so with numbers ([PR-11](docs/history/lessons-ledger.md), [PR-12](docs/history/lessons-ledger.md)).
- **Committed harnesses.** Every test, benchmark, fixture and measurement script is committed; nothing that matters lives only in a session's files ([TS-08](docs/history/lessons-ledger.md)). Show each new test failing with the old bug restored ([TS-04](docs/history/lessons-ledger.md)).
- **Money before presentation** (PLAN §0 call 1). Money work never waits for map, 3D or art work; it runs on the mini-Boston fixture. In weeks 1–2, map and 3D work is only what PLAN §14 lists. From week 3 until the first dollar, no look, 3D or art work starts; from then until M3 is signed off, at most one session in three is look, 3D or art work, and only the items PLAN §10 schedules. The layers a money milestone's exit check needs (lines, stops, demand dots, the code-drawn bus glyph) belong to that milestone. If the first dollar is late on Nov 1, map work stops and every session works on income ([GD-01](docs/history/lessons-ledger.md), [SC-05](docs/history/lessons-ledger.md)). No Steam or desktop session (Electron, packaging, signing, Steam uploads, store material) starts before v1.0 is complete on the preview (target Sun Feb 7 2027) or Mon Mar 1 2027, whichever comes first (D18); the owner's Steamworks and Apple paperwork is not a session.
- **No presentation pivot inside a milestone.** No renderer change after Sun Nov 1, the custom-layer interface included, and never two renderers ([SC-05](docs/history/lessons-ledger.md), [RN-03](docs/history/lessons-ledger.md)). No new sim system after Sun Dec 6 ([SC-08](docs/history/lessons-ledger.md)).
- **Commits.** V1-style messages that say why, with numbers from the sim; no checkpoint commits; never squash ([PR-09](docs/history/lessons-ledger.md), [PR-14](docs/history/lessons-ledger.md)).
- **Questions.** At most five a week to the owner, batched, each with a recommendation ([PR-03](docs/history/lessons-ledger.md)). Record answers in `docs/DECISIONS.md`.
- **Done** means green CI, every doc the change touches updated in the same PR ([PR-06](docs/history/lessons-ledger.md)), and deployed: the deploy job's last step loads the live preview in Playwright with a cache-busting query and finds the SHA in both the build chip and `version.json?run=<run_id>`. Cite that job's result in the next PR's STATUS, never in a PR of its own (D27); report nothing as deployed before it passes.
- **Playtest freeze.** No merge to `main` from 18:00 the day before a playtest until its notes are committed; sessions keep working on branches. Testers record the build chip's SHA at the start and end of each session, and the two must match ([PR-13](docs/history/lessons-ledger.md)).

## Architecture guardrails

- Sim truth lives only in `src/sim`, run in a worker on a fixed step. No DOM, React, MapLibre, `Date` or `Math.random` there ([AR-04](docs/history/lessons-ledger.md), [AR-06](docs/history/lessons-ledger.md), [AR-09](docs/history/lessons-ledger.md)).
- `src/ui` and `src/render` import only `sim/rules` and sim types. Each rule is one predicate shared by the cursor card, the command and the drawing ([GD-05](docs/history/lessons-ledger.md)).
- Only `src/platform/` touches `localStorage`, IndexedDB, Cache Storage, the service worker, `navigator.storage`, fullscreen, external links, reloads, `version.json` or Electron's preload bridge. This keeps the Steam build a packaging job. The web preview registers no service worker, keeps no Cache Storage and writes no save migrations: on a schema change, older web saves are set aside under a backup key with a one-line notice ([DP-06](docs/history/lessons-ledger.md)), never overwritten, and the save envelope and Export session file record the build SHA (D12). A failed lazy chunk, worker load or tile read shows one "This build was replaced · Reload" card; that is error recovery, not an update prompt.
- **Desktop builds (D15).** V1's Electron `app://` shell (PLAN §6), with Electron pinned exactly in its own `desktop/package.json` so web PR checks never install it. The origin `app://game` never changes, because saves live under it. Desktop builds never become CI artifacts: anyone signed in to GitHub can download a public repo's artifacts. Signing and notarization run only in dispatch-only macOS jobs, never on a PR and never inside the 8-minute checks: `desktop-sign` holds the certificate and notary key, runs on `main` and `desktop/*` branches with no reviewer, and uploads nothing, so signing fixes never wait for a merge or the owner; `desktop-release` holds the Steam credentials (and its own copy of the signing secrets), runs from `main` only with the owner as required reviewer, and is the only job that runs `steamcmd`, inside the macOS job that signed. Secrets never appear in logs, files or messages. CI uploads and sets builds live only on password-protected beta branches; only the owner sets a build live on a default branch. The demo build uses its own app name and userData path, so its storage under `app://game` stays apart from the full game's, and the full release's platform work (Steamworks, disk saves, Steam Cloud) sits behind a build flag the demo build turns off, so a demo hotfix from `main` never ships it (I16).
- One renderer: MapLibre GL JS, pinned exactly. three.js only inside the vehicle custom layer, lazy-loaded. Render only on change; never set paint properties per frame ([RN-04](docs/history/lessons-ledger.md)).
- Neither the 2D/3D camera mode, the light/dark theme nor the demo flag changes a sim number, a save byte or a rule verdict; the demo stops only in the UI (PLAN §6, I16).
- **Two themes, one generator** (D13): both styles come from one generator and two token sets. The style, palette and contrast tests and I13 run on every theme that exists: light from week 1, dark from week 13, when its token set lands (PLAN §10). Until then they run on light, and the generator only has to accept a token set; building the dark set early is look work and waits (Money before presentation). I12's geometry runs once, on light. A colour change is not done until every existing theme passes.
- **The build chip:** every web build shows its commit SHA on screen at 12 px in the OSM-attribution corner (it counts toward I13), read at build time through `src/platform/`; test reports and playtest notes cite it.
- Players' browsers never fetch source data, and the game loads only its own files: no live APIs, no third-party tiles or fonts (Afacad Flux is self-hosted) ([WD-01](docs/history/lessons-ledger.md)).
- City files come only from the dispatch-only bake job, from pinned, hashed inputs. The deploy never bakes and fails on a missing or mismatched city file. A rebake reaches the preview when its `cities/index.json` change merges; the city revision freezes with content on Jan 17, and after that a rebake PR needs the owner's OK. On Steam a rebake reaches players only in a build the owner sets live.
- No existing transit in the city (D17): the bake turns bus lanes into general lanes and removes stops, stations, routes, rail and ferries; gate G10 checks it. MBTA data is a bake-time calibration input only and never ships. "© OpenStreetMap contributors" stays visible whenever the map shows.
- Build the art pipeline only as far as the artist's delivered files need ([RN-07](docs/history/lessons-ledger.md)). Git LFS before any binary lands ([DP-11](docs/history/lessons-ledger.md)).
- Budgets are tests (PLAN §6): every bus at least its family's minimum length (≥20 px) at the three I12 cameras; menu ≤200 KiB gzip, model chunk ≤200 KiB, recompute ≤150 ms (I14); `chunkSizeWarningLimit` stays at Vite's default; PR checks within 8 minutes. Slower checks go nightly and never block.

## GitHub Pages deploy gates (from `Intralines@7af45b1:CLAUDE.md:20-47`)

1. The branch is listed under `on.push.branches` in the deploy workflow.
2. The branch is allowed by the `github-pages` environment. A miss fails in about 2 s with no logs.
3. `cancel-in-progress: false`, so a run on another branch never cancels a real deploy.
4. Pages source is "GitHub Actions", never "Deploy from a branch".
5. After a deploy, its last step loads the live URL in Playwright with a cache-busting query and polls `version.json?run=<run_id>` until it and the build chip show `GITHUB_SHA`; Pages reportedly caches every file for about 10 minutes (PLAN §11 has the source and date).
6. Every merge to `main` deploys the preview, always (D12). The deploy workflow has no tag trigger and no `LAUNCHED` switch: tags never publish anything. `index.html` references only content-hashed assets, so a reload shows the newest build. **Retain previous assets:** Pages replaces the whole site, so the deploy copies the last two deploys' hashed `assets/` and city files into the new artifact (V1's `Intralines@7af45b1:scripts/retain-assets.mjs`, `d66e6dc`); without it an open tab or a cached `index.html` loads chunks that 404 ([DP-01](docs/history/lessons-ledger.md)). The e2e swap test (PLAN I15) guards it.

## Versioning and the changelog

- **Only the owner creates versions**, by typing `/ship <version>` ([.claude/skills/ship/SKILL.md](.claude/skills/ship/SKILL.md); `disable-model-invocation: true` keeps Claude from starting it). Nothing else adds a version heading to `CHANGELOG.md`, changes a version number or creates a `v*` tag: not at the end of a session, not at a milestone, not because a plan, agent, file or schedule says so. If the owner asks for a release in words, ask them to type `/ship <version>`. A version publishes nothing new on the web: the release PR's merge redeploys the preview like any merge, and the tag publishes nothing. Uploading or setting live a Steam build never creates a version, and `/ship` never uploads to Steam. Every Steam build is identified by its SHA and shows whatever version `CHANGELOG.md` holds at that commit. The demo is never given its own version heading or `v*` tag. The full release is normally built from a commit the owner has `/ship`ped.
- Every change a player would notice adds its entry under `## [Unreleased]` in the same commit: a `- ` bullet under `### Added`, `### Changed`, `### Fixed` or `### Removed`, in a player's words, and true of the build as merged. Tests, CI, refactors and docs get no entry. Delete the "Nothing yet" line with the first entry.
- Run `node scripts/changelog.mjs check` after touching the changelog, and `node --test scripts/changelog.test.mjs` after editing `scripts/changelog.mjs` (`npm run test:scripts` runs it with the other script tests; the directory form `node --test scripts/` fails on Node 22). CI ([.github/workflows/changelog.yml](.github/workflows/changelog.yml)) runs both on every PR, on pushes to the default branch and on `v*` tags; "Versions only via /ship" is a required status check on `main`. It fails any version heading not added by its own commit titled exactly `Release v<version>` (one parent, only `CHANGELOG.md` and package files changed), any `v*` tag not on that commit, any later edit to released notes, and a `package.json` version other than `0.0.0` or the newest release. It cannot tell who made a commit: this rule and the owner's yes inside `/ship` are the guard. `.claude/settings.json` makes `git tag`, tag pushes and `changelog.mjs release` ask for approval in every mode; that is a speed bump, not a boundary.
- Anything that shows the version or SHA (the build chip, `version.json`) reads it from `CHANGELOG.md` and git at build time; never type a version number anywhere else ([PR-15](docs/history/lessons-ledger.md)). Milestone tags such as `prototype` never start with `v`.
